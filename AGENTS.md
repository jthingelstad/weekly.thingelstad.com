# Repository guide — weekly.thingelstad.com

Operational notes for working in this repo. Human-facing overview lives in
[`README.md`](README.md). Site detail: [`apps/site/AGENTS.md`](apps/site/AGENTS.md).

## What this repo is — a render surface

**WT Builder (`wt-builder`) publishes; `librarian-thing` keeps the archive; this repo renders.**
WT Builder authors each issue and commits the 11ty inputs here on send. The canonical issue store
(`data/issues/{N}/archive.md`), the corpus, and the Librarian/Thingy Lambda live in `librarian-thing`
(renamed from `studio-thing` 2026-08-28; the Studio application is retired). This repo builds the 11ty
site from the committed inputs and publishes it to S3 behind CloudFront (GitHub Pages until
2026-10-26).

Do not look for the pipeline, `data/issues`, or `librarian-core` here — they're upstream. The
architecture model lives in `librarian-thing/ALIGNMENT.md`; the website handoff in WT Builder's
`src/server/publish.ts`.

## The handoffs — what gets pushed in

WT Builder's website send commits one file per issue (which triggers the render below):

- `apps/site/archive/{N}.md` — the generated issue page.

There is no separate issue index. The build derives it from the pages' front matter
(`apps/site/lib/issueIndex.js`); the `emails.json` WT Builder once merged into on every send was
retired 2026-09-29.

`librarian-thing` pushes one file on corpus rebuilds:

- `data/librarian/graph.json` — topic graph for the topic pages.

**Never edit `apps/site/archive/*.md` (or the pushed files) here.** They're regenerated upstream and
overwritten by the next handoff. Fix the issue in WT Builder and re-send; historical repairs go in
`librarian-thing/data/issues/{N}/archive.md`.

## Data files in `apps/site/_data/`

- **Pushed in** (don't hand-edit): `data/librarian/graph.json` by `librarian-thing`.
- **Owned by this repo:** `stats.json` — subscriber + Stripe figures, fetched by *weekly's own CI* (a
  landing-page presentation concern).
- **Hand-authored** (edit directly): `site.js`, `support.json`, `quotes.json`, `survey.json`,
  `faq.json`.
- **Vendored** (don't hand-edit): `sites.json` — a byte-for-byte copy of the thingelstad.com
  `shared/sites.json`, the one list of Jamie's sites. Edit it there, then `npm run sites:sync` here
  and commit the copy (CI checks out only this repo). `npm run sites:check` fails on drift; `npm test`
  runs it, the deploy workflow cannot (there is no sibling checkout in CI). It feeds the sites
  strip (see `apps/site/AGENTS.md`). The same sync copies the shared type (`shared/tokens.css` and
  `shared/fonts/`) into `apps/site/css/shared/`, and the check covers it too.

`archiveStats.js` computes stats at build time from the issue pages' front matter (records, streaks,
per-year breakdowns), read through `apps/site/lib/issueIndex.js`; `topics.js` and `redirects.js` read
the same index.

## GitHub Actions — `.github/workflows/deploy.yml`

Render-only. Triggered by push to `main` (a handoff commit) + manual `workflow_dispatch`. Steps:
`npm ci` → validate tracked documentation links → `npm audit` (advisory: `continue-on-error`, so an
upstream advisory never blocks publishing) → fetch landing-page stats → `npm run build` (11ty) →
`npm run build:search` (Pagefind) → install Playwright Chromium → `npm run test:e2e` (the real gate;
on failure `test-results/` + `playwright-report/` upload as a 7-day artifact) → upload the build as the
`site` artifact. The `deploy` job (main only) then runs `npm run deploy:aws` as the delivery role. No
Lambda, no corpus build — those run in `librarian-thing`.

The site moved from GitHub Pages to S3 and CloudFront on 2026-10-26 (Jamie: "Approved: move
weekly.thingelstad.com to S3 and CloudFront with real 301 redirects, Pages kept until DNS cutover").
Both deployed until the DNS moved the same day; then the Pages job, `CNAME` and `.nojekyll` went. See
"S3 and CloudFront" below.

## S3 and CloudFront

Three stacks, generated by `infra/templates.mjs` into `infra/generated/` (`npm run infra:generate`;
a unit test fails when the committed JSON is stale) and deployed **from this Mac as the cloud-engineer
identity** with `npm run infra -- certificate|site|delivery` (`--plan` prints the change set and
stops). `infra/deployment.json` records their names, tags and outputs.

- `weekly-certificate`: the ACM certificate, validated by a CNAME at Namecheap. DNS is Jamie's to edit.
  Keep the validation record: renewal needs it. The `weekly` record is a CNAME to the distribution's
  `cloudfront.net` name. ACM checks CAA along that CNAME chain: while `weekly` was a CNAME to
  `jthingelstad.github.io`, GitHub's CAA (DigiCert, Let's Encrypt, Sectigo) refused Amazon and the
  first certificate FAILED. Pointing `weekly` at GitHub's A records for the hour of validation let the
  check fall through to `thingelstad.com`'s CAA, which allows `amazon.com`. Any other site moving off
  Pages hits the same wall.
- `weekly-site`: a private, versioned bucket (old versions kept 90 days) behind CloudFront with origin
  access control; AWS's CachingOptimized policy (no query string in the key, so `?ref=` variants share
  one copy); security headers plus `Access-Control-Allow-Origin: *` as Pages sent; 403/404 serve
  `/404.html`; a 5xx alarm to `weekly-thing-librarian-alarms`; access logs to the CloudWatch log group
  `/weekly/web-access`, kept 14 days, with no client IP or query string (the other sites' shape). The
  alias and certificate attach only once the certificate is ISSUED (rerun `npm run infra -- site`).
- `weekly-delivery`: the role GitHub Actions assumes (`vars.AWS_DEPLOY_ROLE_ARN`), `main` only. It can
  publish into the bucket, update the redirect store and clear the cache; it cannot change the stacks.

**Redirects are real 301s.** The build writes `_redirects.json` (`apps/site/redirects-map.njk`: every
redirect page, path to target). Each deploy copies it into the distribution's CloudFront key value store,
and the viewer-request function (`infra/viewer-request.mjs`) answers those paths with a 301 that keeps
the query string. The same function sends a bare path to its slash form and serves `index.html` for
directory URLs; the extensionless files it passes through are listed in its `FILES` (an e2e test keeps
the map equal to the redirect pages and `FILES` equal to the build). The meta-refresh redirect pages are
still built (the map is read from them) but never reached on CloudFront.

**Content types and caching** are set per file by `scripts/publish-plan.mjs`: `/rss` and the Atom
feeds go out as `application/xml` (CloudFront does not compress `application/atom+xml`, and `/feed.xml`
is 290 KB raw, 44 KB gzipped), `/podcast.xml` as RSS, Pagefind's index as bytes. Pages are five minutes
in browsers and a day in CloudFront; fonts and images a week.

`npm run deploy:aws` (`scripts/deploy-aws.mjs`) refuses unless the site stack's live template equals
`infra/generated/site.json`, so infrastructure goes out first, on its own. It uploads the files whose
MD5 changed (`--all` re-uploads everything, needed after a `publish-plan.mjs` change), syncs the
redirect store, deletes what the build no longer writes, clears the cache, and reads the result back
through the CloudFront domain (the front page as built, `/rss`'s type, a redirect, the slash form, a
404). Tinylytics refuses the `cloudfront.net` host, so analytics only count on the real domain.

## Secrets

This repo holds only what its own concerns need — the credentials for the landing-page stats fetch.
Publishing secrets live in WT Builder; corpus/Lambda secrets live in `librarian-thing`. The deploy
assumes the delivery role through GitHub's OIDC token; no AWS keys are stored.

## Conventions worth knowing (site-only)

- **Pagefind UI** reset blocks CSS overrides — use `!important`. `data-pagefind-filter` survives until
  reindex.
- **Tinylytics kudos** overwrites innerHTML — render heart/label via CSS `::before` so they survive.
- **Don't hand-edit generated files** (`apps/site/archive/*.md`, the pushed `_data/*.json`,
  `data/librarian/graph.json`) — fix upstream in WT Builder or `librarian-thing`.
- **e2e tests** (`tests/e2e/`) are Playwright specs against the rendered site + Thingy redirects.
  Playwright serves the already-built `_site/` (Pagefind index included) with `python3 -m http.server`
  on :8080, so the tests see what deploys. Locally run `npm test` (checks the vendored `sites.json`,
  runs the unit tests, builds, indexes, then tests); bare
  `npm run test:e2e` expects `npm run build:all` first. The deploy workflow installs Chromium and runs
  them before uploading the `site` artifact the deploy publishes.
- **Agent guide compatibility:** `AGENTS.md` is canonical everywhere in this repo (root and
  `apps/site/`) and each `CLAUDE.md` is a one-way symlink beside it.
  `npm run test:docs` validates every tracked Markdown symlink and both root entry points.
