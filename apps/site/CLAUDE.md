# apps/site/ — project memory

Operational notes for working in the Eleventy site. Human-facing overview lives in [`README.md`](README.md). Repo-wide architecture is in [`../../CLAUDE.md`](../../CLAUDE.md).

## Eleventy invocation

Invoked from the **repo root** via `eleventy --config apps/site/eleventy.config.js` (see `package.json`'s scripts). The output dir `_site/` stays at the repo root so CI's `upload-pages-artifact` step picks it up unchanged. **Don't move `_site/` under `apps/site/`** — CI assumes the repo-root location.

- **Input:** `apps/site` / **Output:** `_site` (at the repo root)
- **Template formats:** `njk`, `md`
- **Markdown:** `markdown-it` with `markdown-it-anchor` for heading IDs (Pagefind needs them for anchored search hits)
- **Collections:** `issuesByNumber` (ascending), `issuesByDate` (newest first)
- **Filters:** `dateFormat`, `dateShort`, `currentYear`, `numberFormat`, `year`, `slice`, `truncate`, `issueNumberBase`, `xmlEscape`, `markdownify`, `extractToc`, `groupByYear`
- **Passthrough copy:** `img/`, `css/`, `CNAME`, `favicon.svg`, `_nojekyll`

## The archive build flow

`apps/site/archive/{N}.md` is **generated** — not the editing surface. `pipeline/content/content.py build` reads `data/issues/{N}/{archive.md, metadata.json, links.json}` and writes `apps/site/archive/{N}.md` with the 11ty front-matter contract (adds `layout: archive`, `permalink: /archive/{N}/`, `tags: ["issue"]`, audio fields from `data/audio/manifest.json`).

Every generated file carries an inline notice:

```md
<!-- Generated by pipeline/content/content.py from data/issues; do not edit directly. -->
```

**Editorial fixes go upstream** in `data/issues/{N}/archive.md`. Re-run `pipeline/content/content.py build` (or `make build`) to regenerate.

## `_data/` files

Data files mix hand-authored content and pipeline-generated output. Knowing which is which matters because hand-edits to generated files get clobbered on the next build.

**Generated** (don't hand-edit):
- `emails.json` — lightweight issue index. Written by `pipeline/content/content.py build`.
- `stats.json` — subscriber + Stripe figures. Written by `make stats`.
- `status.json` — pipeline state for `/ops/`. Written by `pipeline/status.py`.
- `voiceSamples.json` — home-page pull-quotes. Written by `make refresh-copy` (`pipeline/content/refresh_marketing_copy.py`) — explicit, not in CI.

**Hand-authored**:
- `site.js`, `support.json`, `quotes.json`, `survey.json`, `topics.js`, `redirects.js`, `assets.js` — edit directly.

**Computed at build time** (JS data files run during 11ty):
- `archiveStats.js` — totals (links, words, domains), per-year breakdowns, records, streaks. Reads `emails.json`.
- `supportTotals.js` — supporter program totals. Reads `support.json` + `stats.json`.
- `faq.js` — re-exports `apps/librarian/lambda/shared/faq.json` so the site and Thingy share one FAQ source. **Don't edit `faq.js`** — edit the shared JSON.

## Voice samples — `make refresh-copy`

The "How It Sounds" home-page pull-quotes are regenerated on demand by an LLM pipeline, not hand-curated. Two files drive it:

- `pipeline/content/marketing-brief.md` — the generator's persistent context (voice, themes, guardrails). Hand-editable; treated as ground truth on the next run. The canonical *human* voice doc is `docs/voice-and-style.md`, which this brief should track.
- `_data/voiceSamples.json` — generated pull-quotes, pulled verbatim from real issues with verification.

```bash
make refresh-copy-dry   # prints proposed changes, writes nothing
make refresh-copy       # writes voiceSamples.json + marketing-brief.md
```

Stratified sample of ~32 issues over the last 2 years; Sonnet picks 3-5 verbatim pull-quotes and rewrites the brief. Machine-verified verbatim against issue bodies. Expected cost: ~$0.20-0.40 per run. Run logs land in `tmp/copy-refresh-<timestamp>.json` (gitignored). Not wired into CI — refreshes are explicit, human-initiated. Expected workflow: run, review `git diff`, commit.

A previous version of the pipeline also generated `_data/copy.json` (hero/value-prop/CTAs) via an Opus second pass. That output didn't deliver enough quality; it was removed and the home page is now hand-written in `index.njk` directly.

## Pagefind

Runs **after** Eleventy build, indexes the built HTML in `_site/`. CI does this as a separate step (`npx pagefind --site _site`). Local: `make build` runs it; `make serve` does not. UI styling overrides need `!important` because Pagefind UI resets its container's CSS.

## Subscribe forms + reader-recognized state

Multiple subscribe forms across the site read from `localStorage`:

- `tokenKey` (JWT, hash-only) — drives the "you're already subscribed" recognized state
- `emailKey` (plaintext, prefill only)

A recognized reader sees: dim subscribe button + placeholder email. **No new panels** — just the existing form acknowledges them. The "Forget me" link clears both keys; label is **Forget me** site-wide, not Logout / Sign out / Use different email.

## Conventions

- **Never edit `apps/site/archive/*.md` directly.** Edit `data/issues/{N}/archive.md` and run `make build`.
- **Tinylytics site UID** lives in `_data/site.js` (currently `a2YQr3ZMqkySNYSwz4uF`). It's safe in the repo — the UID is a public identifier.
- **Buttondown newsletter `domain` field MUST stay empty.** Setting it confirms a 404 on the custom-domain check. (Memory; matters for any code that writes to Buttondown's newsletter config.)
- **Generated archive files** include a 7-day-cache header set via the `_headers` file (if used). Don't fight the build over caching.
- **CSS** lives in `apps/site/css/style.css`; email CSS lives in `content/buttondown/newsletter/buttondown-email.css` (paste into Buttondown's Custom CSS field).
